## 1) Detailed report: will this work on Windows + Linux?

### 1.1 Topology: what targets exist and how they connect

**Top-level `NOBS_CLiP/CMakeLists.txt`** drives everything:

* Detects platform: `WINDOWS` if `WIN32`, `LINUX` if `UNIX AND NOT APPLE`. Hard-fails on macOS and MinGW.
* Sets global compile flags/definitions and C++17 standard.
* Finds Boost (headers primarily) and creates an `INTERFACE` library: `nobs_boost_headers`.
* Adds subdirectories in this order:

  1. `BOLT`  (must produce `boltMathBackend`)
  2. testing setup + `testutils` (if tests enabled)
  3. `modules` (if enabled)
  4. `common`
  5. `core` (main exe)
  6. `FAT_P`
  7. `sim/snopt` (if sim mode)

**`BOLT/CMakeLists.txt`**:

* Chooses backend via `BOLT_MATH_BACKEND` (default `"mkl"`).
* Adds `us/${BOLT_MATH_BACKEND}` and requires that target `boltMathBackend` exists afterwards.
* For 64-bit indexing it defines `MKL_ILP64` *if* MKL backend is selected.

**`BOLT/us/mkl/CMakeLists.txt`**:

* Creates `boltMathBackend` as a **STATIC** library.
* Hard-requires `MKLROOT` in the environment and uses `mkl_link_tool` to compute the exact link line on Linux.

**`core/CMakeLists.txt`**:

* Builds executable `nobs-clip`.
* Links in `boltMathBackend` plus internal libs.

**`testutils/CMakeLists.txt`**:

* Creates `nobs_testutils` as a STATIC library **with no sources** (currently empty).

## 1.2 The cross-platform “good parts”

### A) MSVC CRT selection (Boost mismatch prevention)

Top-level correctly uses:

* `/MT` or `/MD` via `CMAKE_MSVC_RUNTIME_LIBRARY`

This addresses the common “Boost built with different runtime” link failures on Windows.

### B) Linux std::filesystem auto link

Top-level probes whether `-lstdc++fs` is needed and sets `NOBS_STDCXXFS_LIB` accordingly. That’s correct and avoids breaking newer GCC toolchains by forcing `stdc++fs`.

### C) PUBLIC propagation of MKL dependencies (static library ordering correctness)

`boltMathBackend` is STATIC, and the file explicitly tries to ensure MKL libraries are `PUBLIC` so the final executable sees them. That is the correct approach to Linux link ordering.

## 1.3 The concrete “won’t work as-is” issues

### Issue 1 — MKL is a hard configure-time requirement

`BOLT/us/mkl/CMakeLists.txt` *fatal-errors* if `MKLROOT` is not defined in the environment.

So **any** of these will fail at CMake configure time:

* a clean Linux box without oneAPI sourced
* a Windows machine without setvars invoked (or MKL not installed)
* CI runners without MKL

Even if you’re just trying to build parts of the project that don’t need MKL.

### Issue 2 — `core/CMakeLists.txt` references non-existent source paths in this zip

It references paths like:

* `${CMAKE_SOURCE_DIR}/modules/classes/...`
* `${CMAKE_SOURCE_DIR}/modules/sensor_models/...`

But in the zip tree, `modules/` only contains `modules/test/...`.

Result: **configure/generate will fail** because `add_executable()` is given missing sources.

(If your real repo has those directories, then this zip is not self-consistent. But as presented, it will not build.)

### Issue 3 — Empty STATIC library for `nobs_testutils`

CMake generators/toolchains vary in how they handle a static library with no sources. Some allow it, some error or produce odd “no objects” behavior.

Your own comment in the file acknowledges this: it should be `INTERFACE` if empty.

### Issue 4 — “Real SNOPT” is Linux-only + hard-coded archive expectations

Real SNOPT requires:

* Linux
* `NOBS_SNOPT_INCLUDE_DIR` set
* `NOBS_SNOPT_LIB_DIR` set
* a specific archive naming/layout

Windows is effectively “simulate-only”.

## 2) Dependency install and “positioning” instructions

### 2.1 CMake + compiler baseline

* CMake ≥ 3.15 (you already require 3.15).
* C++ compiler:

  * Windows: Visual Studio 2019/2022 (MSVC)
  * Linux: GCC or Clang (GCC recommended if you’re using oneAPI MKL link tooling, but Clang works too if your libstdc++ / OpenMP situation is coherent)

---

### 2.2 Boost (headers primarily, tests/bench may need libs depending on code)

#### Windows (recommended: vcpkg)

1. Install vcpkg, then:

   * `vcpkg install boost` (or at least `boost-headers` if you truly only use headers)
2. Configure with:

   * `-DCMAKE_TOOLCHAIN_FILE=<vcpkg-root>/scripts/buildsystems/vcpkg.cmake`

Alternative: install Boost prebuilt and set:

* `-DNOBS_BOOST_INCLUDE_DIR=C:\path\to\boost`

#### Linux (apt)

* Ubuntu/Debian:

  * `sudo apt-get update`
  * `sudo apt-get install -y libboost-all-dev`

Or source install (if you need a specific Boost version):

* build Boost, then pass:

  * `-DNOBS_BOOST_INCLUDE_DIR=/path/to/boost`

**Positioning rule**:

* Ensure your Boost headers path contains `boost/version.hpp` at:

  * `<include>/boost/version.hpp`

---

### 2.3 Intel MKL / oneAPI (for the MKL backend)

#### Linux (oneAPI)

1. Install Intel oneAPI Base Toolkit (includes MKL).
2. In each shell session (or in CI), set environment:

   * `source /opt/intel/oneapi/setvars.sh`

This defines `MKLROOT` and other needed vars.

**Verify**:

* `echo $MKLROOT`
* Check MKL include exists: `$MKLROOT/include/mkl.h`

If you rely on `mkl_link_tool`, ensure it exists at one of:

* `$MKLROOT/tools/mkl_link_tool/mkl_link_tool`
* `$MKLROOT/../mkl/latest/tools/mkl_link_tool/mkl_link_tool` (varies by install)

#### Windows (oneAPI)

1. Install Intel oneAPI Base Toolkit.
2. Run Intel oneAPI command prompt (or call):

   * `"<oneapi>\setvars.bat"`
3. Confirm `MKLROOT` exists:

   * `echo %MKLROOT%`

**Positioning rule**:

* `$MKLROOT/include` must contain MKL headers
* `$MKLROOT/lib` (or appropriate `lib/intel64`) must contain MKL libs

---

### 2.4 SNOPT

You currently support:

* **Simulated SNOPT**: included (no external install)
* **Real SNOPT**: Linux only, user-supplied

For real SNOPT you must provide:

* `-DNOBS_SIMULATE_SNOPT=OFF`
* `-DNOBS_SNOPT_INCLUDE_DIR=/path/to/snopt/include`
* `-DNOBS_SNOPT_LIB_DIR=/path/to/snopt`

And ensure the archive exists at:

* `${NOBS_SNOPT_LIB_DIR}/lib/libsnopt7_cpp.a`

Plus Fortran runtime (`gfortran`) available.

---

If you want the “final form” that stops link issues with Boost/MKL for real builds, the next step after this patch is to **stop using global `add_compile_options/add_link_options`** for link-critical flags and instead attach link items per-target (`target_link_libraries`, `target_compile_options`) — because global flags make it easy to accidentally apply LTO/PGO/OpenMP settings inconsistently across libraries and executables (classic cause of “works on one machine, fails on another”).
