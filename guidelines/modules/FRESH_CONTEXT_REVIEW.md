# Fresh-context review

Applies when checking work after a context reset, or validating a change to the
corpus's onboarding and required reading. A writer's familiarity is not evidence
that a new AI can absorb the project. A second opinion in a loaded session is not
a context reset. Use existing authorization; this procedure grants no model access,
delegation, edits, or external actions.

## Prepare the input boundary

Use a new context with no inherited conversation or private task memory. Provide:

- The current copied guidelines, starting at their normal index, with actual
  project facts, durable constraints, rationale, and precedents intact.
- The current code/tests or document under review and necessary tool configuration.
- A brief task objective and truthful source coordinates; not an answer to endorse.

Exclude the writer's review, prior correctness verdicts, design conversation, and
incidental bug/fix narratives. Do not make the reviewer load archives or case
histories merely because they exist. Preserve a binding contract or decision-changing
rationale at its canonical home; context reset is not permission to hide it. If an
essential source also contains old verdicts, provide a faithful scoped view and
record the boundary. Never silently omit an unresolved obligation.

Follow [CORE](../CORE.md) for onboarding and task routes. The reviewer records what
it read and which sources it used for decisions. If prior conclusions leak into
the context, label the result as an informed review rather than a fresh-context pass.

## Exercise decisions, not recitation

For corpus changes, select concrete tasks covering the changed behavior. Establish
the expected obligations before dispatch, outside the reviewer's input. For example:

| Task | Evidence of useful judgment |
|---|---|
| A routine guideline clarification | Finds the relevant rule without imposing teaching-document form or reading unrelated procedures |
| A repeated mistake, resolved trade-off, and anticipated failure | Distinguishes count-only accountability, an existing-rule clarification, and new reusable judgment |
| A C++ change with aggregate fields, members, static state, and constants | Applies exact house naming and formatting; identifies applicable checks |
| Passing behavior with a disputed architectural property | Checks the enforcing mechanism instead of inheriting a green verdict |
| A result citation versus benchmark implementation | Preserves the claim's evidence limits; loads full benchmark machinery for implementation |

Use actual small artifacts or explicit synthetic fixtures, not leading questions
that state the desired answer. Ask for decisions, canonical references, required
reads, and the relevant checks. A summary of the crash course is insufficient.
For product review, choose representative contracts and failure boundaries in scope.

## Evaluate and integrate

The reviewer returns findings and evidence, without editing the reviewed material.
The task owner checks source references and counterexamples, records actual reads,
decisions, checks run, and limits, and repairs confirmed defects under existing
authority. Missing tools or an interrupted review are unavailable evidence, not a pass.

If the review exposes a failure in fresh loading, fix its cause and re-evaluate the
affected behavior in a new context. There is no arbitrary cycle quota. Preserve
failure-prevention rules while removing needless reading; a shorter response alone
does not show better decisions. Use [Peer bridge](PEER_BRIDGE.md) when invoking a
configured bridge, and [Review and delivery](REVIEW_AND_DELIVERY.md) for findings.

Record the input snapshot, task, observed outcome, and limitations outside mandatory
onboarding. A fresh-context result applies only to its tested tasks and source state;
it proves neither universal model reliability nor untested product correctness.
