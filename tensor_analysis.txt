3. KEY FINDING: FIXED VS STATIC TENSOR DUPLICATION
================================================================================

FixedTensor (FixedTensor.h) vs StaticTensor (TensorMath.h)
----------------------------------------------------------

THEY ARE ESSENTIALLY THE SAME CONCEPT WITH DIFFERENT NAMES AND IMPLEMENTATIONS:

Similarities (95% overlap):
  ✓ Both use compile-time shape specification
  ✓ Both store data in std::array (stack allocation)
  ✓ Both support element access via operator[] and operator()
  ✓ Both provide element-wise operations (+, -, *, /)
  ✓ Both provide scalar operations
  ✓ Both provide reduction operations (sum, mean, max, min)
  ✓ Both provide matrix multiplication (matmul)
  ✓ Both provide vector operations (dot, norm, normalize)
  ✓ Both use template metaprogramming for compile-time checks

Key Differences:

1. NAME AND NAMESPACE:
   - FixedTensor uses FixedTensor<T, Dims...>
   - StaticTensor uses StaticTensor<T, Shape<Dims...>, Policy>

2. SHAPE SPECIFICATION:
   FixedTensor<float, 3, 4>       // Direct template parameters
   StaticTensor<float, Matrix<3, 4>>  // Wrapped in Shape<> struct

3. ARITHMETIC POLICY:
   - FixedTensor: No policy support (always unchecked)
   - StaticTensor: Three policies available:
     * UncheckedPolicy (default)
     * CheckedPolicy (uses CheckedArithmetic.h)
     * SaturatingArithmeticPolicy (clamping on overflow)

4. ALIGNMENT:
   - FixedTensor: No explicit alignment
   - StaticTensor: alignas(32) for SIMD optimization

5. DEPENDENCIES:
   - FixedTensor: Zero library dependencies
   - StaticTensor: Depends on CheckedArithmetic.h

6. SIMD OPTIMIZATION:
   - FixedTensor: No SIMD
   - StaticTensor: Has simd_dot() for float vectors (AVX2)

7. TYPE ALIASES:
   FixedTensor provides:
     - FixedVec2f, FixedVec3f, FixedVec4f
     - FixedMat2x2f, FixedMat3x3f, FixedMat4x4f
   
   StaticTensor provides:
     - Vec2f, Vec3f, Vec4f (UncheckedPolicy)
     - Mat2x2f, Mat3x3f, Mat4x4f
     - Vec2c, Vec3c (CheckedPolicy variants)
     - Vec2s, Vec3s (SaturatingArithmeticPolicy variants)

8. COMPUTE_INDEX IMPLEMENTATION:
   - FixedTensor: Variadic template recursion
   - StaticTensor: Array + loop (simpler)

4. PROBLEMS AND INCONSISTENCIES
================================================================================

P1. DUPLICATE FUNCTIONALITY (MAJOR):
    Problem: FixedTensor and StaticTensor do the same thing
    Impact: Code duplication, maintenance burden, user confusion
    Severity: HIGH
    
    Evidence:
      - Both files ~400 lines
      - Identical operations: +, -, *, /, sum, mean, max, min, matmul, dot, norm
      - Same use case: compile-time fixed-size tensors
      - Different names for the same concept

P2. FILE PROLIFERATION (MEDIUM):
    Problem: 8 header files for tensor functionality
    Impact: Complex include graph, harder to navigate
    Severity: MEDIUM
    
    Breakdown:
      - 3 tensor implementations (Tensor, FixedTensor, StaticTensor)
      - 1 storage helper (TensorStorage - barely used)
      - 1 operations file (TensorEinsum - only works with Tensor)
      - 2 integration files (BinarySerializer_Tensor, EqualityTensor)
      - 1 utility file (ComparisonTolerances - 17 lines only)

P3. INCONSISTENT NAMING (MINOR):
    Problem: Mixed naming conventions
    Examples:
      - "FixedTensor" vs "StaticTensor" for same concept
      - "Tensor" (dynamic) vs "FixedTensor"/"StaticTensor" (static)
      - File: "TensorMath.h" contains "StaticTensor" class
      - Test file typo: "test_TensorCompareSeialize.cpp"

P4. TENSORSTORAGE UNDERUTILIZED (MEDIUM):
    Problem: TensorStorage.h is designed but not used
    Evidence:
      - Tensor.h line 2316: "Using std::shared_ptr for now - consider TensorStorage"
      - TensorStorage provides 10-20% performance gain according to docs
      - File exists but commented as "optional" upgrade
    Impact: Performance left on table, dead code

P5. COMPARISONTOLERANCES.H TOO SMALL (MINOR):
    Problem: Entire file is 17 lines with 3 constexpr values
    Impact: Could be folded into EqualityTensor.h
    File Contents:
      constexpr double kDefaultEpsilon = 1e-10;
      constexpr float kDefaultEpsilonF = 1e-6f;  
      constexpr double kStrictEpsilon = 0.0;

P6. DEPENDENCY BLOAT IN TENSOR.H (MEDIUM):
    Problem: Main Tensor.h includes 15+ dependencies
    Impact: Long compile times, tight coupling
    Note: Many are debug-only (EnhancedBoundsChecking, ViewLifetimeTracking)
    
P7. EINSUM ONLY WORKS WITH DYNAMIC TENSORS (MINOR):
    Problem: TensorEinsum.h only accepts Tensor<T>, not FixedTensor/StaticTensor
    Impact: Can't use einsum with compile-time tensors
    
P8. TEST FILE NAMING INCONSISTENCY (MINOR):
    Problem: test_TensorCompareSeialize.cpp has typo in filename
    Should be: test_TensorCompareSeri**a**lize.cpp

5. ARCHITECTURAL ISSUES
================================================================================

A1. THREE-WAY SPLIT:
    Current: Tensor (dynamic) + FixedTensor (static) + StaticTensor (static)
    Problem: Why two static tensor implementations?
    
    User confusion:
      "Which one should I use for a compile-time matrix?"
      "What's the difference between FixedTensor and StaticTensor?"
      "Why are there two?"

A2. TENSOR STORAGE NOT INTEGRATED:
    Design: TensorStorage provides custom refcounting for 10-20% speedup
    Reality: Tensor still uses std::shared_ptr
    Question: Why create TensorStorage if not using it?

A3. SEPARATE SERIALIZATION FILE:
    BinarySerializer_Tensor.h is 423 lines
    Could be integrated into Tensor.h or BinarySerializer.h
    Pros of current: Modular, optional
    Cons: Another file to track

A4. POLICY INCONSISTENCY:
    - StaticTensor has arithmetic policies (Checked/Unchecked/Saturating)
    - FixedTensor has no policies
    - Tensor has no arithmetic policies (but has iterator/concurrency policies)
    
    Should policies be unified across all tensor types?

6. DETAILED CONSOLIDATION RECOMMENDATIONS

RECOMMENDATION 1: MERGE FixedTensor and StaticTensor
Priority: HIGH
Complexity: MEDIUM

Proposed Approach:
  Keep: StaticTensor (more features, better design)
  Deprecate: FixedTensor (simpler but less capable)
  
  Rationale:
    - StaticTensor has arithmetic policies (safety options)
    - StaticTensor has SIMD optimization
    - StaticTensor has better alignment for performance
    - StaticTensor follows modern C++ best practices
    - FixedTensor offers no unique value
  
  Migration Path:
    1. Add type aliases to StaticTensor for FixedTensor compatibility:
       template<typename T, size_t... Dims>
       using FixedTensor = StaticTensor<T, Shape<Dims...>>;
    
    2. Mark FixedTensor.h as [[deprecated]]
    3. Update all tests to use StaticTensor
    4. Remove FixedTensor.h after one release cycle
  
  Benefits:
    - Eliminate ~400 lines of duplicate code
    - Reduce maintenance burden by 50% for static tensors
    - Clear user choice: Tensor (dynamic) vs StaticTensor (compile-time)
    - Keep all policy features

RECOMMENDATION 2: CONSOLIDATE SMALL FILES
Priority: MEDIUM
Complexity: LOW

     - Only 17 lines, 3 constants

RECOMMENDATION 3: INTEGRATE OR REMOVE TensorStorage
Priority: MEDIUM  
Complexity: HIGH

  Option A: Actually use TensorStorage in Tensor.h

  Recommendation: Choose Option A

    - Follow through on the design

  matrix(1, 2) = 5.0f;

  #include "StaticTensor.h"

  float s = sum(matrix);
  
  // Old FixedTensor name still works (deprecated)
  FixedTensor<float, 3, 4> old_style;  // Alias to StaticTensor
  
  // Policy-based checking
  StaticTensor<int, Shape<10>, CheckedPolicy> safe;
  safe[0] = checked_add<ThrowOnErrorPolicy>(INT_MAX, 1);  // Throws

  Tensor<float> t({100, 200});  // Runtime shape
