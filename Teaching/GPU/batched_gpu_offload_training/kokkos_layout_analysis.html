Kokkos Layout Analysis Why LayoutLeft Is Wrong for This Pipeline, and How to Get It Right

This document teaches you how to choose the correct Kokkos memory layout for 2D views on GPU. It walks through a real mistake — LayoutLeft applied everywhere in a batched pipeline — shows you visually why it produces fully uncoalesced memory access, and gives you the three-step procedure to get the right answer for your own kernels.

1. What LayoutLeft and LayoutRight Actually Do

For a 2D view V(i, j) with dimensions (4 rows, 8 cols):

LayoutLeft: the leftmost index (i) varies fastest. Walking V(i, 0) → V(i, 1) → V(i, 2) for fixed i means jumping by nrows each step.

LayoutRight: the rightmost index (j) varies fastest. Walking V(i, 0) → V(i, 1) → V(i, 2) for fixed i means stepping by 1 each time.

Neither is inherently better. The question is always: which index do adjacent threads in a warp vary?

2. How Kokkos Maps Threads on GPU

The MDRangePolicy iteration order is not automatic. The Rank template accepts optional iteration-order parameters. The default on CUDA aligns with LayoutLeft (leftmost rank fastest). For LayoutRight views, you must explicitly request right iteration order:

using mdrange_right_2d = Kokkos::MDRangePolicy<
    Kokkos::Rank<2, Kokkos::Iterate::Right, Kokkos::Iterate::Right>>;

With explicit Iterate::Right, adjacent threads in a warp get adjacent values of the rightmost index:

mdrange_right_2d({0,0}, {BATCH, NFREQ}) — 32 threads in one warp:

With Iterate::Right: all 32 threads share the same window w, each gets a consecutive frequency bin j, j+1, j+2, ...
With default Iterate::Left: threads would vary w instead — wrong for LayoutRight views.

For TeamPolicy(BATCH, ORDER+1): one team per window. team_rank() gives consecutive indices within that window. This is always right-iteration by construction — no iteration-order parameter needed.

5. The cuSOLVER Exception

The solver matrices are not stored as 2D views. They are flat 1D buffers with explicit index arithmetic:

view_1d d_A("matrices", BATCH * ORDER * ORDER);

// Each matrix is a contiguous block, column-major inside:
size_t base = w * ORDER * ORDER;
d_A(base + row + col * ORDER) = value;

This is correct. cuSOLVER dictates the memory layout — batch-contiguous blocks, column-major inside each block. The pointer array references these contiguous blocks:

d_Aptr[k] = raw_A + k * ORDER * ORDER;  // each pointer → contiguous 32×32 block

Do not convert this to a multidimensional Kokkos view. The flat buffer with manual indexing is the right abstraction for vendor library interop where the library owns the layout contract.

6. The Rule

For every 2D+ Kokkos view accessed inside a parallel dispatch:

1
Identify the execution policy. MDRangePolicy, TeamPolicy, or nested TeamThreadRange.
2
Determine which index adjacent threads vary.
• MDRangePolicy: depends on Iterate direction. CUDA default is Iterate::Left (leftmost rank fastest). Use explicit Iterate::Right for rightmost rank fastest.
• TeamPolicy: team_rank() within one team
• Nested TeamThreadRange: the inner range index
3
Make that index contiguous in memory.
• Thread varies the leftmost index → LayoutLeft
• Thread varies the rightmost index → LayoutRight
Data Role View Shape Thread Varies Correct Layout
Windowed signal (window, sample) sample (rightmost) LayoutRight
PSD output (window, freq_bin) freq_bin (rightmost) LayoutRight
cuSOLVER matrices flat 1D, manual indexing N/A — vendor contract flat view_1d

7. The Wrong Reasoning Chain

The mistake follows a specific pattern. Every step is individually correct. The chain is wrong because it skips the thread mapping analysis.

The broken chain:

"GPU wants coalescing"
→ "coalescing means contiguous memory access"
→ "LayoutLeft makes the first index contiguous"
→ "therefore LayoutLeft is the GPU layout"

Missing step: "which index do adjacent threads vary in MY kernel?"

Without that step, you've mapped a hardware property (coalescing) to a Kokkos type (LayoutLeft) without going through the actual thread-to-index mapping. The conclusion can be right or wrong depending on the kernel — and you'll never know which because you didn't check.

The correct chain:

"GPU wants coalescing"
→ "coalescing means adjacent threads access adjacent addresses"
→ "my pipeline treats each window as a local problem — the local index should vary across threads"
→ "local index is the rightmost dimension in my views"
→ "rightmost must be contiguous → LayoutRight"
→ "MDRange default on CUDA is Iterate::Left — must set Iterate::Right explicitly"
→ "layout + iteration order + access pattern all agree"

The performance difference: coalesced vs fully strided global memory access — typically 10–30× on bandwidth-bound kernels. Both layouts produce correct numerical results. They produce them at very different speeds.
