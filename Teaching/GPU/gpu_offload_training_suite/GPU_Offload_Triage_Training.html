Part I — The code and its structureTop ↑

The program is a single file — hot_loop.c — implementing an iterative solver pattern common in scientific computing.  Here is the outer loop.  This is where the program spends all of its time — 50,000 iterations, five function calls per iteration, each feeding its output to the next:

hot_loop.c — the outer loop 50,000 iterations · ~200 GFLOP total
// These two control everything — change N to resize the problem static const int nOuter = 50000; // outer iterations static const int N = 224; // matrix dimension (224² = 50,176 entries) static const int bufLen = 4096; // state buffer length for (int it = 0; it < nOuter; ++it) { // PHASE A transformBuffer(stateIn, stateOut, flags, bufLen); // PHASE B buildMatrix(stateOut, flags, A, N); // PHASE C if (choleskyInplace(A, N) != 0) { cholFail++; for (int k = 0; k < bufLen; ++k) { stateIn[k] *= 0.5; } continue; // shrink & retry } // PHASE D forwardSolve(A, b, y, N); backwardSolve(A, y, x, N); // PHASE E updateState(stateIn, x, bufLen, N); }

Prepares each buffer entry for matrix construction
parallelizable
B
Build SPD matrix — N², direction-dependent, 4-way branch
Builds the SPD matrix A that defines the linear system Ax = b
parallelizable

All five phases are hand-written application code.  The difference is computational character: in A, B, and E, every iteration of the inner loop is independent — computing stateOut[k] doesn't read any other stateOut[j], so all iterations can run simultaneously on a GPU.  In C and D, each step reads the results of all prior steps — column j of the Cholesky needs columns 0 through j−1, so the loop is sequential as written. That qualifier — "as written" — turns out to be the whole story.

The actual source code

Phase A transformBuffer() 4,096 entries · 3 branches · log / exp / tanh
/* Phase A: buffer transform with 3-way magnitude branching */ static void transformBuffer(const double *restrict in, double *restrict out, double *restrict flags, int n) { for (int k = 0; k < n; ++k) { const double v = in[k]; const double a = fabs(v) + 1e-12; const double lv = safeLog(a); // FP64 log() if (lv > 5.0) { // large-magnitude path const double s = (v >= 0.0) ? 1.0 : -1.0; out[k] = s * exp(0.5 * lv); // FP64 exp() flags[k] = 1.0; } else if (lv < -5.0) { // tiny-magnitude path: stabilized Taylor const double v2 = v * v; out[k] = v * (1.0 + 0.5*v2 + 0.125*v2*v2); flags[k] = -1.0; } else { // mid-magnitude: full transcendental mix const double t = tanh(v); // FP64 tanh() out[k] = exp(lv) * t - 0.1 * v; // FP64 exp() flags[k] = (v >= 0.0) ? 0.5 : -0.5; } } }

FP64 transcendentals

Every entry hits log().  Most hit exp() or tanh().  FP64 throughput varies dramatically by GPU class: consumer NVIDIA (e.g.  RTX 5080) is 1:64 of FP32 — 0.83 vs 53 TFLOPS.  Data-center GPUs like V100 or A100 have 1:2, but the cost is still real.  Every transcendental call pays this ratio.

3-way branch → warp divergence

Threads within the same 32-thread warp that take different paths must serialize.  If half a warp goes large-magnitude and half goes mid, both paths execute and inactive threads are masked.  Up to 3× serialization in the worst case.

But parallelizable

Each iteration k is independent — stateOut[k] doesn't read any other stateOut[j].  All 4,096 entries can run simultaneously on a GPU.  The flags[k] output propagates to Phase B's 4-way branch.

Phase B rawAij() + buildMatrix() 50,176 entries · direction-dependent · 4 branches
/* Raw matrix entry: direction-dependent, 4-way branching */ static inline double rawAij(int i, int j, const double *restrict buf, const double *restrict flags, int n) { // Direction-dependent index mapping: // multiplier 7 on row, 11 on column // → rawAij(i,j) ≠ rawAij(j,i) in general const int bi = (i * 7 + 3) & (bufLen - 1); const int bj = (j * 11 + 5) & (bufLen - 1); const double xi = buf[bi], xj = buf[bj]; const double fi = flags[bi], fj = flags[bj]; if (i == j) { return xi*xi + 0.5*xj*xj + (double)n + 1.0; } const int d = (i > j) ? (i - j) : (j - i); const double decay = exp(-0.01 * (double)d); // FP64 exp() per entry // 4-way branch on flag product and distance if (fi*fj > 0.25) { return 0.30*xi*xj * decay; } else if (fi*fj < -0.25) { return -0.10*(xi-xj) * decay; } else if (d < 4) { return 0.20*(xi+xj) * decay; } else { return 0.02*(xi-xj) * decay; } } /* Build symmetric matrix: MUST compute both directions and average */ static void buildMatrix(const double *buf, const double *flags, double *A, int n) { for (int i = 0; i < n; ++i) { for (int j = 0; j <= i; ++j) { double aij; if (i == j) { aij = rawAij(i, i, buf, flags, n); } else { // Average both directions for true symmetry const double fIj = rawAij(i, j, buf, flags, n); const double fJi = rawAij(j, i, buf, flags, n); aij = 0.5 * (fIj + fJi); } A[i * n + j] = aij; if (i != j) { A[j * n + i] = aij; } } } }

Direction-dependent indexing

The row index uses multiplier 7, the column uses 11.  So rawAij(3, 5) reads buffer positions (3×7+3)&mask = 24 and (5×11+5)&mask = 60, but rawAij(5, 3) reads (5×7+3)&mask = 38 and (3×11+5)&mask = 38.  Different entries, different values.  Every GPU variant must compute both directions and average — a naïve lower-triangle mirror gives a different matrix and breaks the checksum.

The FP64 exp() cost

Every off-diagonal entry calls exp(-0.01 × d) for the decay factor.  At N² that's ~50,000 FP64 exp() calls per iteration × 50,000 iterations ≈ 2.5 billion exp() calls total.  On a 1:64 FP64 GPU, each one is very expensive.

4-way branching

The branch path depends on the product of flags from Phase A and diagonal distance.  On a GPU, warp divergence can cause up to 4× serialization.

Phase C choleskyInplace() 68.1% at N=224 · serial · N columns
/* Cholesky: A = L Lᵀ, right-looking, column-by-column */ /* Column j READS all columns 0..j-1 → serial dependency */ static int choleskyInplace(double *restrict A, int n) { for (int j = 0; j < n; ++j) { /* pivot: subtract contributions from prior columns */ double diag = A[j*n + j]; for (int k = 0; k < j; ++k) // ← reads cols 0..j-1 { const double l = A[j*n + k]; diag -= l * l; } if (!(diag > 0.0)) { return -1; } diag = sqrt(diag); A[j*n + j] = diag; /* trailing column below diagonal */ const double invDiag = 1.0 / diag; for (int i = j + 1; i < n; ++i) { double s = A[i*n + j]; for (int k = 0; k < j; ++k) // ← reads cols 0..j-1 { s -= A[i*n + k] * A[j*n + k]; } A[i*n + j] = s * invDiag; } } return 0; }

Concrete example: computing column 3

Pivot: diag = A[3,3] − L[3,0]² − L[3,1]² − L[3,2]², then L[3,3] = sqrt(diag).  Each subtracted term needs a fully computed prior column.  Column 3 cannot begin until columns 0, 1, and 2 are done.

Trailing column: For each row i = 4..223: s = A[i,3] − L[i,0]·L[3,0] − L[i,1]·L[3,1] − L[i,2]·L[3,2], then L[i,3] = s / L[3,3].  Same dependency — every term reads from prior columns.

68.1% of total CPU time at N=224

In the clean Advisor export, Cholesky accounts for 68.08% of the N=224 run, then grows to 85.33% at N=512 and 93.49% at N=1024.  At N=224, column j does j multiply-accumulates for the pivot alone, plus j × (N−j−1) for the trailing column.  Total: ~3.7 MFLOP per outer iteration × 50,000 = ~185 GFLOP.

Advisor will stamp this "Dependency"

And it's correct for this loop.  Column j reads all prior columns.  But the operation (Cholesky factorization) has vendor GPU implementations (cuSOLVER's dpotrf) that use a completely different blocked, multi-SM algorithm with no structural resemblance to this serial loop.  Appendix C walks through the blocked algorithm step by step.

Phase D forwardSolve() + backwardSolve() serial recurrence · trip count = N
/* Ly = b — row i reads rows 0..i-1 */ static void forwardSolve(const double *L, const double *b, double *y, int n) { for (int i = 0; i < n; ++i) { double s = b[i]; for (int k = 0; k < i; ++k) // ← serial recurrence { s -= L[i*n + k] * y[k]; } y[i] = s / L[i*n + i]; } } /* Lᵀx = y — row i reads rows i+1..n-1 */ static void backwardSolve(const double *L, const double *y, double *x, int n) { for (int i = n - 1; i >= 0; --i) { double s = y[i]; for (int k = i + 1; k < n; ++k) // ← serial recurrence { s -= L[k*n + i] * x[k]; } x[i] = s / L[i*n + i]; } }

Each solve step is a dot product against solved values

To compute y[i], the forward solve reads y[0] through y[i-1] — every value that has already been solved — multiplies each by a coefficient from row i of L, accumulates, and divides by the diagonal.  The backward solve does the same in reverse: x[i] reads x[i+1] through x[n-1] using column i of L.  There is real arithmetic inside each row, but the row-to-row dependency is strictly sequential.

Concrete example: forward solve, row 3

s = b[3]
s -= L[3,0] · y[0] — needs y[0] already solved
s -= L[3,1] · y[1] — needs y[1] already solved
s -= L[3,2] · y[2] — needs y[2] already solved
y[3] = s / L[3,3]

Row 3 cannot begin until rows 0, 1, and 2 are done.  Row 4 cannot begin until row 3 is done.  The entire solve is a strict chain of N steps — no parallelism across rows.

The indexing distinction

The forward solve reads across row i: L[i*n + k].  The backward solve reads down column i: L[k*n + i].  Same stored lower triangle, different access patterns — the backward solve has worse cache locality on a row-major layout.

O(N²), ~1% of runtime

Much smaller than the Cholesky's O(N³).  At N=224 the solves take ~1% of runtime.  But Advisor will still flag them with Trip_Count and Launch_Tax — only N outer iterations.  The GPU decision is not "launch one thread per row"; it is whether to replace the solve with a library operation (cusolverDnDpotrs or KokkosBlas::trsm).

Phase E updateState() 4,096 entries · feeds back to Phase A
/* Solution diffused back into buffer with damped sign-mixing */ /* THIS is the state-carrying path: buf → next iter's Phase A */ static void updateState(double *buf, const double *x, int bufLen, int n) { for (int k = 0; k < bufLen; ++k) { const int src = k % n; const double up = x[src]; double w; if ((k & 3) == 0) { w = 0.9; } else if ((k & 3) == 1) { w = -0.7; } else { w = 0.3; } buf[k] = w * buf[k] + (1.0 - fabs(w)) * up; } }

The feedback path

This function writes into buf — the same array Phase A reads on the next iteration.  Iteration 50,000 depends on the output of iteration 49,999.  Outer iterations cannot be batched independently.

The sign-mixing mask

The weight w cycles through three values based on k & 3: +0.9, −0.7, +0.3 (with k&3==2 and k&3==3 both getting 0.3).  The negative weight at k&3==1 means some buffer entries are subtracted from, not added to.  This prevents the state from converging monotonically and keeps the dynamics alive across 50,000 iterations.

The modular index

x[k % N] maps the N-element solution vector across the 4,096-element buffer.  Each solution element feeds ~18 buffer entries.  This spreading is what couples the linear-algebra solution back into the full state.

For GPU

Trivially parallelizable — every iteration k is independent.  Also tiny: 4,096 entries × a few FLOPs, <1% of CPU runtime.

Why this is hard to offload

Count the complications.  Each one affects the GPU offload decision differently.

⛓

Serial dependencies in C and D

Column j of the Cholesky reads all prior columns.  The triangular solves have the same structure.  A GPU running these loops as written would serialize onto one execution unit while paying memory latency the CPU avoids.

⑂

Branching everywhere

Phase A has 3 code paths.  Phase B's rawAij has 4 branches plus a diagonal check.  On a GPU, divergent branches within a warp serialize — threads that take different paths can't run simultaneously.

∫

FP64 transcendentals

Phases A and B call log, exp, tanh — all FP64.  The cost depends on the target: consumer NVIDIA is 1:64 FP64:FP32, data-center (V100, A100) is 1:2.  Either way, FP64 transcendentals are significantly slower than FP32.

↺

State carries across iterations

Phase E writes into the buffer that Phase A reads next iteration.  Iterations can't be batched independently — each depends on the prior one's output.

⊞

Direction-dependent indexing

rawAij(i,j) ≠ rawAij(j,i) due to the row/column multiplier asymmetry.  Every GPU variant must compute both directions and average.  A naïve lower-triangle mirror gives a different matrix.

◧

Small working set

The matrix footprint is N² × sizeof(double).  The state/buffer footprint is controlled by BUF_LEN, not by 4N.  At N=224 and BUF_LEN=4096, the matrix is 224²×8 = 401,408 bytes — about 392 KiB, or roughly 400 KB — and one double buffer is 4096×8 = 32,768 bytes, or 32 KiB.  That small working set fits comfortably in cache, so the CPU is running this fast from cache.  The GPU has to beat raw cached-CPU throughput, which is hard at small N.

What the loop table actually says

The hot phase is C, not E.  Advisor knows this: Cholesky is 68.1% of the N=224 run, 85.3% of the N=512 run, and 93.5% of the N=1024 run in the clean exports.  It still does not offload Cholesky because the source loop is dependency/latency bound as written.  That is the key lesson: hot does not mean offloadable.

The only accepted offloads are tiny updateState() loops at N=512 and N=1024. Those loops are genuinely parallel, but they are only 0.0795% and 0.0551% of the application. Even an 11.46× loop speedup at N=1024 barely moves the whole program because there is almost no runtime there to accelerate.

Part III — The first real win: MKL replaces the linear algebraTop ↑

The original hot loop spends most of its time in the hand-written Cholesky factorization and the two hand-written triangular solves.  Advisor correctly says those source loops are not attractive automatic GPU offload targets.  The next engineering move is not loop offload. It is operation replacement: keep phases A, B, and E exactly as they are, but replace phases C and D with tuned LAPACK routines from Intel oneAPI MKL.

What MKL is
Intel oneAPI Math Kernel Library (MKL) is Intel's vendor-tuned implementation of BLAS, LAPACK, FFT, sparse kernels, and related math routines for CPUs.  In this document we use two LAPACK entry points through the C LAPACKE interface: LAPACKE_dpotrf() for Cholesky and LAPACKE_dpotrs() for the triangular solves.  The application still builds the same SPD matrix and solves the same system Ax = b; only the implementation of that dense linear algebra changes.
What changes — and what does not
Phases A, B, and E are intentionally identical to the scalar baseline.  That matters pedagogically: any speedup in this section is almost entirely due to replacing the serial dense linear algebra with library code.  This is a fair CPU-library baseline, not a GPU projection.

Exactly which source functions disappear

The scalar baseline spelled out three routines in source: choleskyInplace(), forwardSolve(), and backwardSolve().  The MKL baseline removes all three from the hot path.  One library call factorizes the matrix; one library call solves the system. The mathematical contract is the same, but the implementation strategy is completely different.

Row-major matters here

The application stores A as a full row-major dense array.  The code therefore calls the LAPACKE row-major interface: LAPACK_ROW_MAJOR with 'L'.  After dpotrf, the lower triangle holds the Cholesky factor L.  The upper triangle is not the primary output and does not carry the post-factorized semantics.

One right-hand side

This application solves one vector right-hand side per outer iteration, so nrhs = 1.  The code copies b into x, then dpotrs overwrites x with the solution. That preserves the original b vector for later iterations and for checksum consistency.

Failure handling is preserved

If dpotrf returns a positive info, the matrix was not numerically positive definite at that pivot. The program treats that like the scalar baseline: increment cholFail, shrink the state buffer, and continue.  Negative info means an argument error and is treated as a hard solve failure.

Why MKL is faster

▦

Blocked algorithm instead of scalar recurrence

The hand-written Cholesky is a straightforward right-looking scalar loop: for each column j, subtract previous-column contributions, take a square root, then update the rest of the column. MKL does not execute that exact scalar structure.  LAPACK implementations use blocked algorithms that factor small panels and then update trailing submatrices with dense matrix kernels (see Appendix C for an animated walkthrough).

⇄

More Level-3 BLAS style work

Blocked dense linear algebra converts large parts of the update into matrix–matrix style work with high arithmetic intensity.  That is exactly what CPUs and caches like: many floating-point operations per byte moved.  The scalar baseline performs the same math but exposes much less of that structure to the compiler and runtime.

⚙

Vendor tuning: vectorization, cache, alignment

MKL kernels are hand-tuned for Intel CPUs.  They exploit SIMD vector instructions, unrolling, register blocking, cache-aware panel sizes, and tuned memory access patterns.  The implementation already aligns allocations to 64 bytes, which helps these kernels operate efficiently on dense arrays.

☷

Threading when the matrix is big enough

Threaded MKL can partition the dense factorization and solve work across cores, but that has startup, synchronization, and cache-coherence costs.  Threading wins at all three measured sizes, but the margin grows with N: at N=224 threaded MKL is 1.2× faster than sequential; at N=512 it is 1.3×; at N=1024 it is 1.5×.  The O(N³) factorization scales into threading better as N grows.

⌁

The outer-loop recurrence still exists

MKL does not solve the state-carrying dependence across iterations.  Phase E still writes the next iteration's input buffer.  That is why this section is an operation-replacement win, not yet a full orchestration or GPU-offload solution.

≈

The math stays the same

This matters for trust.  The matrix construction, right-hand side, retry behavior, and state update are preserved.  The checksum remains the continuity check that the optimized implementation is solving the same problem, not a different one.

Why this is not Cholesky

There is no global order saying column 0 finishes before column 1, column 1 before column 2, and so on.  A kernel launch orders one kernel after the previous kernel, but it does not order iterations inside the same kernel by index.

Inside naiveCholeskyColumn, two iterations such as (i=20,j=3) and (i=20,j=7) can run at the same time.  The j=7 iteration reads A(20,3) while the j=3 iteration is responsible for writing it.  That is a read/write race on the matrix entry, not just an inefficient schedule.

The wrong triangular solves: rows launched as if independent

The forward solve is a strict prefix recurrence.  Row i reads y[0..i−1]. A flat parallel_for over i gives no guarantee that those earlier rows have already written y.  The backward solve has the same problem in reverse for x.

Part V — The naïve GPU port: hand-rolled KokkosTop ↑

Part III showed that replacing the hand-written Cholesky with MKL gives a 2.6–11× speedup on CPU. The natural next question: what if we port the whole thing to the GPU instead?  The hand-rolled Kokkos variant (hot_loop_kokkos.cpp) does exactly that — a faithful, correct, single-source GPU port of the original five-phase loop.  It compiles for CUDA, HIP, SYCL, OpenMP, and Serial from one file.  The checksums match.  And it is slower than the CPU at every size.

The result before the explanation
At N=224, the hand-rolled GPU variant takes 141.657 seconds — 4.7× slower than the 30.128-second CPU baseline in the BAT/CMake sweep.  At N=1024 it takes 129.177 seconds versus the CPU's 67.102.  This is not a bug.  It is the structural consequence of porting serial recurrences to a massively parallel machine.

What the variant does differently

The port is not a blind copy-paste.  It makes three genuine improvements over the C baseline, and it avoids the race conditions that would silently corrupt a naïve parallel_for over the Cholesky.

⊞

Decay LUT

The C baseline recomputes exp(-0.01 × |i−j|) inside every call to rawAij. At N=224 with lower-triangle fill that is ~25,000 calls per iteration × 50,000 iterations ≈ 1.25 billion redundant FP64 exp() calls.  The Kokkos variant precomputes a 224-entry lookup table once before the outer loop.  Every rawAij call becomes a table read.

⚙

Fused factor + solve

Phases C and D execute in a single TeamPolicy<>(1, AUTO) kernel — one team of threads cooperating via TeamThreadRange and team_barrier().  No host synchronization between factorization and the two triangular solves.  This eliminates three kernel launches per iteration and the host-side round-trips between them.

∅

On-device accumulators

Cholesky failures increment a 0-D device View via atomic_inc.  The checksum accumulates via atomic_add into another 0-D View.  Both are read back once after the outer loop.  This avoids ~50,000 device→host synchronizations that would cost ~250 ms total.

What this kernel does

One team executes a left-looking Cholesky factorization column by column.  Each column has a team-parallel reduce (dot product), a single-thread pivot check and diagonal write, a barrier, a team-parallel trailing column update, and another barrier.  The two triangular solves follow the same row-by-row pattern.  A checksum tap at the end avoids per-iteration device→host synchronization.

Why this is slow on the GPU

TeamPolicy(1, AUTO) means one team = one thread block = one SM.  On an RTX 5080 with 84 SMs, that is 83 SMs sitting idle during the entire Cholesky and both triangular solves.  The GPU's advantage — massive parallelism across SMs — is not used.

Within the one active SM, the parallel_reduce over k < j starts with trip count 0 at column 0 and grows to N−1 at the last column.  For the first ~32 columns, there is not even enough work to fill one warp.  The team_barrier after every column forces a synchronization point that prevents any overlap between columns.

The forward and backward solves are worse

Each row's dot product has trip count equal to the row index (forward) or N minus the row index (backward).  Row 0 has zero work.  Row 3 has 3 multiply-accumulates.  The team reduces over these tiny work items with a barrier between every row — N barriers per solve, 2N total for both.  At N=224 that is 448 additional barriers with near-zero useful work between most of them.

Why the GPU loses to a cached CPU

◧

TeamPolicy(1, AUTO) occupies one SM.  The rest of the GPU does nothing during the Cholesky factorization and both triangular solves — the phases that dominate runtime.  Phases A, B, and E use all SMs but collectively account for under 10% of CPU time.

⛓

Each column requires a team_barrier after the pivot and another after the trailing update.  At N=224 that is 448 barriers per Cholesky, plus 448 more for the two solves — 896 synchronization points per outer iteration, 44.8 million across the full run.

⏱

GPU memory latency without cache advantage

The CPU runs the Cholesky from L2 cache (the 400 KB matrix fits).  The GPU's global memory is higher-latency.  The L2 on the RTX 5080 is 64 MB — more than enough — but the access pattern (strided column reads under LayoutRight) produces cache-line waste that the CPU's smaller, faster L2 handles better for this access pattern.

∫

FP64 at 1:64 on consumer hardware

The RTX 5080's FP64 throughput is 1/64th of FP32 — about 0.83 TFLOPS.  Every multiply-accumulate in the Cholesky inner loops, every sqrt() for the diagonal, and every division in the solves runs at this reduced rate.  The CPU has no such penalty for FP64 work.

What Advisor predicted — and what happened

In Part II, Advisor rejected the Cholesky and solve loops with verdicts of Dependency and Latencies.  The hand-rolled Kokkos variant confirms that assessment empirically. The serial column-to-column dependency is faithfully preserved in the TeamPolicy kernel — each team_barrier() enforces the same ordering that the CPU's sequential loop uses.  Moving that structure to the GPU did not remove the dependency.  It added launch overhead, memory latency, and FP64 throughput penalties while losing the CPU's cache advantage.

The decay LUT and fused kernel are genuine engineering improvements that would help in a variant with better parallelism.  But they cannot overcome the fundamental mismatch: a serial algorithm on a parallel machine.

The lesson
A correct GPU port of a serial algorithm is still a serial algorithm.  Correctness and performance are independent properties.  The right question is not "can I run this code on the GPU" — you can — but "does the GPU have enough parallel work to justify the overhead?"  For unblocked Cholesky at N=224, the answer is no.  Appendix C shows how the blocked algorithm changes this.

What changed

Three vendor library calls replace the 896-barrier single-team kernel.  Each call dispatches to a blocked algorithm that distributes work across all 84 SMs.  The host sees three kernel launches instead of one, but each launch does orders of magnitude more useful work per clock cycle.

Why cuSOLVER uses all 84 SMs

cuSOLVER's dpotrf implements a blocked (right-looking) Cholesky (Appendix C).  It partitions the matrix into panels of width ~32–64, factors each panel with a single-SM kernel, then updates the trailing submatrix with a GEMM that saturates all SMs.  At N=224, the trailing-update GEMMs are small (at most 224×224 tiles), so SM utilization is modest.  At N=1024, the trailing-update GEMM at the first panel is 992×992 — enough to fill 84 SMs with useful work.

Why MKL still wins at N=224

At N=224, the 400 KB matrix fits entirely in the CPU's L2 cache.  MKL's blocked Cholesky runs from cache with full FP64 throughput and zero launch overhead.  cuSOLVER on the RTX 5080 pays three costs: roughly seven host-submitted operations per iteration (tens of microseconds of overhead), FP64 at 1/64th of FP32 (~0.83 TFLOPS versus the CPU's ~130 GFLOPS across 24 threads), and the panel factorization running on a single SM for each of the ~4–7 panels at this size.  The O(N³) work at N=224 (~3.7 MFLOP per factorization) is simply not enough to amortize these costs.

Why cuSOLVER wins at N=512 and above

At N=512, the factorization is ~45 MFLOP — 12× more work than N=224.  The trailing-update GEMMs grow quadratically, giving cuSOLVER's 84 SMs enough parallel work to overcome the per-launch overhead.  At N=1024, the factorization is ~358 MFLOP and the trailing-update dominates, making the GPU's aggregate memory bandwidth and compute throughput decisive.  The crossover around N=400–512 is where the O(N³) work first exceeds the GPU's fixed per-launch and per-panel costs.

Why operation replacement works on both sides

The lesson from Parts III through VII is the same lesson, applied twice.  The hand-written Cholesky in hot_loop.c is an unblocked, left-looking, single-threaded factorization. It computes the correct answer, but it does not exploit the hardware — not the CPU's vector units and multiple cores, not the GPU's thousands of threads and dozens of SMs.

MKL and cuSOLVER both replace that loop with a blocked algorithm (Appendix C): partition the matrix into panels, factor each panel, update the trailing submatrix with a high-performance GEMM.  The GEMM is the key — it is the part that maps to hardware parallelism (SIMD lanes on CPU, thread blocks on GPU). The source loop's serial column-to-column dependency still exists inside each panel, but the trailing-update GEMM dominates the arithmetic and it is embarrassingly parallel.

This is the "as written" distinction from Part I made concrete.  The serial recurrence is a property of the source loop, not the mathematical operation.  Replace the loop, and the operation becomes parallelizable.

Megakernel — all phases in one __global__ cooperative_groups · block 0 does linear algebra
__global__ void megakernel(double* __restrict__ stateIn, double* __restrict__ stateOut, double* __restrict__ flags, double* __restrict__ A, const double* __restrict__ b, double* __restrict__ bWork, const double* __restrict__ decayLut, double* __restrict__ checksum, int N, int bufLen) { extern __shared__ double scratch[]; cg::grid_group grid = cg::this_grid(); // Phase A — all blocks, stride loop phaseADev(stateIn, stateOut, flags, bufLen); grid.sync(); // Phase B — all blocks, stride loop phaseBDev(stateOut, flags, A, decayLut, N, bufLen); grid.sync(); // RHS reset — all blocks, stride loop resetRhsDev(b, bWork, N); grid.sync(); // Linear algebra — block 0 ONLY if (blockIdx.x == 0) { choleskyBlock(A, N, scratch); forwardSolveBlock(A, bWork, N, scratch); backwardSolveBlock(A, bWork, N, scratch); if (threadIdx.x == 0) { atomicAdd(checksum, bWork[0] - bWork[N/2] + bWork[N-1]); } } grid.sync(); // Phase E — all blocks, stride loop phaseEDev(stateIn, bWork, N, bufLen); }

One kernel, one SM problem

Phases A, B, and E distribute work across the full grid (all 84 SMs).  The Cholesky and solves run on block 0 only — the other 83 blocks hit the grid.sync() barrier and wait.  This is the same structural problem as Part V's TeamPolicy kernel, but the grid barriers are explicit (grid.sync()) instead of implicit (kernel launch boundaries).

Cooperative launch requirements

Cooperative kernels require all thread blocks to be resident simultaneously — the grid size is bounded by SM count times per-block occupancy.  On the RTX 5080 with 256 threads/block and the megakernel's register and shared-memory pressure, that means roughly 84 blocks (one per SM). The kernel uses stride loops, so any grid size within the cooperative limit produces correct results, but the grid cannot grow beyond what the hardware can co-schedule.

The build cost

Cooperative groups require relocatable device code (-rdc=true) and the device runtime library (-lcudadevrt).  RDC can slightly reduce instruction-level optimizations because the compiler must preserve cross-module calling conventions.  For this workload the effect is negligible — the hot path is the hand-rolled Cholesky, which is memory-latency-bound, not instruction-throughput-bound.

The persistent kernel — one launch for the entire run

hot_loop_cuda_persistent.cu takes the megakernel concept to its logical endpoint: the outer loop itself moves inside the kernel.  One cooperative launch, one stream synchronization at the end.  Zero host-side calls during the computation.

Persistent kernel — 50,000 iterations inside one __global__ cooperative launch · outer loop on GPU
__global__ void persistentKernel(double* __restrict__ stateIn, double* __restrict__ stateOut, double* __restrict__ flags, double* __restrict__ A, const double* __restrict__ b, double* __restrict__ bWork, const double* __restrict__ decayLut, double* __restrict__ checksum, int N, int bufLen, int nOuter) { extern __shared__ double scratch[]; cg::grid_group grid = cg::this_grid(); for (int it = 0; it < nOuter; ++it) { phaseADev(stateIn, stateOut, flags, bufLen); grid.sync(); phaseBDev(stateOut, flags, A, decayLut, N, bufLen); grid.sync(); resetRhsDev(b, bWork, N); grid.sync(); if (blockIdx.x == 0) { choleskyBlock(A, N, scratch); forwardSolveBlock(A, bWork, N, scratch); backwardSolveBlock(A, bWork, N, scratch); if (threadIdx.x == 0) { atomicAdd(checksum, bWork[0] - bWork[N/2] + bWork[N-1]); } } grid.sync(); phaseEDev(stateIn, bWork, N, bufLen); grid.sync(); // iter boundary: E writes → next A reads } }

The host side

The host launches one cooperative kernel and waits:

cudaLaunchCooperativeKernel( (void*)persistentKernel, dim3(gridSize), dim3(BLOCK), args, sharedBytes, stream); cudaStreamSynchronize(stream);

The extra barrier

The persistent kernel has 5 grid.sync() calls per iteration — one more than the megakernel.  The extra barrier after Phase E ensures that the state updates are globally visible before the next iteration's Phase A reads them.  In the megakernel, this is provided implicitly by the kernel-launch boundary between iterations.

Constraints

The kernel runs for the full duration (seconds to minutes).  On Linux compute nodes without a display GPU this is fine.  On Windows or any system with a watchdog timer that kills kernels exceeding ~2 seconds, the persistent kernel will be terminated — the megakernel (one launch per iteration) is the fallback.  The cooperative launch also monopolizes the GPU for the entire run: no other process can schedule work on the SMs until the kernel completes.

Streaming Multiprocessor (SM)

The basic compute unit on an NVIDIA GPU.  Each SM contains ALUs, a register file, shared memory, a warp scheduler, and a small L1 cache.  The RTX 5080 used in this document has 84 SMs.  A kernel occupies one or more SMs; the GPU's work distributor assigns thread blocks to SMs as resources become free.  When Parts V and IX say "83 SMs idle," that means the hand-rolled Cholesky is running on one SM while the rest of the GPU sits empty.

▤

Warp

A group of 32 threads that execute in lockstep on the same SM.  All 32 threads in a warp fetch the same instruction at the same time.  If threads in a warp take different branches (warp divergence), the SM serializes the branches — the divergent paths execute one at a time while the other threads are masked off.  Phase B's 4-way branch can cause up to 4× serialization within a warp if adjacent threads hit different branch paths.

▦

Thread block and grid

A thread block is a group of threads (up to 1024) that share an SM's shared memory and can synchronize with __syncthreads().  A grid is the collection of all thread blocks launched by a single kernel.  In Kokkos, a TeamPolicy league maps to the grid, each team maps to a thread block, and TeamThreadRange distributes work within a block.

⌁

FP64:FP32 throughput ratio

Consumer NVIDIA GPUs (GeForce, RTX) have a 1:64 ratio — FP64 runs at 1/64th the throughput of FP32.  Datacenter GPUs (A100, H100) have 1:2.  The hot_loop workload is entirely FP64 (double), so consumer GPUs pay a large throughput penalty.  This is why the RTX 5080 loses to MKL at N=224 even with vendor library kernels: the CPU's FP64 units run at full speed while the GPU's are throttled 64×.

☷

Shared memory

A small, fast scratchpad (up to 228 KB per SM on Blackwell) shared by all threads in a block.  Much faster than global memory but limited in size.  The Phase B TeamPolicy variant caches row-constant values (xi, fi) in shared memory so team threads don't redundantly load from global memory.  The megakernel uses shared memory for the hand-rolled Cholesky workspace.

⚙

Occupancy

The fraction of an SM's maximum resident warps that a kernel actually uses.  Occupancy depends on the kernel's register usage, shared memory usage, and block size.  Higher occupancy helps hide memory latency because the SM can switch to another warp while one is waiting for data.  The hand-rolled Cholesky has low occupancy because only one team of threads is active on one SM.

Appendix B — Data transfer costsTop ↑

The main narrative assumes all working data is resident on the GPU throughout the outer loop.  This appendix explains why that assumption holds for this workload and when it would break down.

Why transfers are negligible here

In the Kokkos and CUDA variants, device memory is allocated once before the outer loop and freed after it.  The state buffer, matrix, RHS vector, solution vector, and decay LUT all live on the GPU for all 50,000 iterations.  The only host↔device transfers are a one-time setup (copy initial state, RHS, and LUT to device) and a one-time readback (copy the checksum and failure count back).  At N=224 the total transferred data is roughly 800 KB — a sub-millisecond operation over PCIe 4.0.  Amortized over 50,000 iterations, the per-iteration transfer cost is effectively zero.

When transfers would dominate

If the application were not an iterative loop — if it performed a single factorization and returned the result to the CPU — the transfer cost would matter.  PCIe 4.0 x16 delivers roughly 25 GB/s in each direction.  A round trip for an N×N FP64 matrix costs:

Blocked-factorization mental model
The panel step still has serial structure, and the TRSM step propagates that panel into the rest of the matrix.  The reason a library implementation can still win is that it exposes the large trailing update as Level-3 BLAS work: many independent dense tiles, high arithmetic intensity, and enough parallel work to occupy many GPU SMs.

The diagram is the conceptual bridge.  The dependency that blocks the source loop lives in the narrow panel, while the dominant arithmetic moves into the lower-right trailing update.  That update is a dense matrix kernel, so the library exposes the parallel work that the original source layout hides.

The unblocked (source) algorithm

The hand-written choleskyInplace() processes one column at a time.  For column j, it subtracts contributions from columns 0 through j−1, takes a square root for the diagonal, then updates the entries below the diagonal.  Column j+1 cannot begin until column j finishes.  The algorithm performs N sequential steps, each touching O(N) data.  The total work is O(N³/3) but the serial chain is N steps long — there is almost no parallelism to exploit within a single column step at small N.

The blocked algorithm

A blocked Cholesky partitions the matrix into panels of width nb (typically 32–256, chosen by the library based on cache size and hardware).  Each step processes one panel in three sub-operations:

1

Panel factorization

Factor the nb columns of the current panel using the unblocked algorithm.  This is still serial column-by-column, but the panel is narrow (nb columns, not N), so the serial portion is short.  This is a Level-2 BLAS operation — O(N × nb²) work, memory-bandwidth-bound.

2

Triangular solve (TRSM)

Solve the triangular system that propagates the panel's factor to the rest of the row block.  This is a Level-3 BLAS operation with moderate parallelism.

3

Trailing-matrix update (GEMM)

Update the lower-right submatrix with a dense matrix–matrix multiply.  This is the dominant operation — it has O(N² × nb) arithmetic with O(N × nb) data, giving arithmetic intensity O(N).  GEMM is embarrassingly parallel and maps perfectly to GPU hardware: thousands of threads computing independent output elements from shared input panels.  This is why the blocked algorithm is fast.

The key insight: the serial recurrence still exists inside the panel factorization, but the trailing-matrix GEMM dominates the arithmetic and it is fully parallel.  As N grows, the GEMM fraction increases and the panel fraction shrinks — which is why the library speedup over the hand-written code grows with N (2.6× at N=224, 7.4× at N=512, 11.2× at N=1024).

The connection to "as written"
The source loop's serial recurrence is real — column j does depend on columns 0..j−1.  But that dependency is a property of the unblocked algorithm choice, not the mathematical operation.  The blocked algorithm reorganizes the same arithmetic so that the dominant work (GEMM) has no such dependency.  This is the "as written" distinction from Part I made concrete: replace the algorithm, and the parallelism appears.

Appendix F — Decision summaryTop ↑

The nine parts of this document produce a concrete decision framework for GPU offload triage.  Here it is, distilled:

1

Profile the code (Part II)

Use Intel Advisor, NVIDIA Nsight, or your profiler of choice to find the hot loops and understand their computational character.  The profiler's loop-level verdict is useful but not final — it answers "should this source loop be offloaded?" not "should this operation be replaced?"

2

Ask whether the loop should still exist (Part III)

If the hot loop implements a standard mathematical operation (factorization, solve, FFT, sort), check whether a vendor library provides a tuned implementation.  If it does, replace the loop with the library call.  This is the highest-leverage optimization and it works on both CPU (MKL, OpenBLAS) and GPU (cuSOLVER, cuBLAS, cuFFT).

3

Understand the failure modes (Parts IV–V)

Flat parallelism over a recurrence is not a slow program — it is a wrong program.  A correct single-team port preserves ordering but wastes hardware.  Both are instructive mistakes that motivate the right answer: use the abstraction that matches the operation.

4

Use the right abstraction for each phase (Part VI)

TeamPolicy and parallel_for for data-parallel phases.  Vendor library calls for dense linear algebra.  Do not force one abstraction to cover both — that is the Part V mistake.

5

Measure the crossover (Part VII)

The CPU wins at small N, the GPU wins at large N, and the crossover depends on the specific hardware, the FP64 throughput ratio, and the operation mix.  There is no universal rule — measure at your sizes on your hardware.

6

Optimize orchestration last (Parts VIII–IX)

CUDA Graphs, stream capture, and launch reduction are second-order optimizations.  They matter only after kernel quality is right.  The persistent kernel has one launch total and is 47× slower than the 7-launch cuSOLVER variant.  Kernel quality first, orchestration second.

LAPACK / MKL (CPU — Part III)

LAPACKE_dpotrf

lapack_int LAPACKE_dpotrf(int layout, char uplo, lapack_int n, double *A, lapack_int lda)

Computes the Cholesky factorization of a real symmetric positive-definite matrix: A = LLᵀ (when uplo='L').  Overwrites the lower triangle of A with the factor L in-place.  Returns 0 on success, a positive integer k if the leading k×k minor is not positive-definite, or a negative value for an invalid argument.

layout: LAPACK_ROW_MAJOR or LAPACK_COL_MAJOR — this workload uses row-major.  n: matrix dimension (224, 512, or 1024).  lda: leading dimension, equal to n for a contiguous matrix.

This is the CPU-side operation replacement in Part III.  MKL's implementation uses a blocked algorithm internally (see Appendix C), selecting a panel width based on the CPU's cache hierarchy.

LAPACKE_dpotrs

lapack_int LAPACKE_dpotrs(int layout, char uplo, lapack_int n, lapack_int nrhs, const double *A, lapack_int lda, double *B, lapack_int ldb)

Solves AX = B using a previously computed Cholesky factor: applies L⁻¹ then (Lᵀ)⁻¹ to each column of B.  Overwrites B with the solution X.  In this workload, nrhs=1 (single right-hand side), so B is a vector.

This replaces the hand-written forwardSolve() and backwardSolve() with a single call.  The combined factor-and-solve path in Part III wraps both dpotrf and dpotrs inside mklFactorAndSolve().

cuSOLVER (GPU — Parts VI–IX)

cusolverDnDpotrf

cusolverStatus_t cusolverDnDpotrf(cusolverDnHandle_t handle, cublasFillMode_t uplo, int n, double *A, int lda, double *workspace, int workspaceSize, int *devInfo)

GPU equivalent of dpotrf.  Factors A = LLᵀ on the device using a blocked algorithm that distributes the trailing-matrix GEMM across all available SMs.  Requires a pre-allocated workspace buffer whose size is queried via cusolverDnDpotrf_bufferSize.  The result status is written to devInfo on device memory (0 = success, >0 = not positive-definite).

In the uploaded source bundle, this is called through the View overload KokkosLapack::potrf(exec, "L", A).  The matrix is a rank-2 LayoutLeft View accessible from the execution space. Some KokkosKernels references and versions also expose an explicit LAPACK-style overload such as potrf(exec, "L", N, A, N); use the overload supported by the installed KokkosKernels version and label snippets accordingly.

cuBLAS (GPU — Parts VI–IX)

cublasDtrsm

cublasStatus_t cublasDtrsm(cublasHandle_t handle, cublasSideMode_t side, cublasFillMode_t uplo, cublasOperation_t trans, cublasDiagType_t diag, int m, int n, const double *alpha, const double *A, int lda, double *B, int ldb)

Solves a triangular matrix equation: B := α × op(A)⁻¹ × B (when side=LEFT).  op(A) is A, Aᵀ, or Aᴴ depending on the trans parameter.  Overwrites B with the solution.

In this workload, trsm is called twice per iteration:

1. Forward solve: side=L, uplo=L, trans=N — solves Ly = b by applying L⁻¹.

2. Backward solve: side=L, uplo=L, trans=T — solves Lᵀx = y by applying (Lᵀ)⁻¹.

Called through Kokkos via KokkosBlas::trsm(exec, "L", "L", "N"/"T", "N", 1.0, A, bWork).  The right-hand side is stored as an N×1 2-D View (bWork) because trsm operates on matrix B, not a vector.  After both calls, column 0 of bWork contains the solution x.

Kokkos parallel patterns (Parts IV–VIII)

Kokkos::parallel_for

Kokkos::parallel_for(label, policy, lambda)

Executes the lambda once for each index in the execution policy's range.  No return value; purely side-effecting.  With RangePolicy(0, n), the lambda receives a single integer index.  With MDRangePolicy, it receives multiple indices.  With TeamPolicy, it receives a team member handle.

Used for Phases A, B, and E in every GPU variant.  A parallel_for call may return before the kernel has completed, and Kokkos does not guarantee iteration order. Completion requires an explicit fence on the execution space, Kokkos::fence(), or another synchronizing operation.  Do not describe ordinary parallel_for dispatch as having an implicit fence after every call.

Kokkos::parallel_reduce

Kokkos::parallel_reduce(policy, lambda, result)

Executes the lambda across all indices, accumulating a scalar result via a reducer.  Each thread computes a partial contribution; the runtime combines them.  In Part V, used inside the TeamPolicy kernel to sum L[j,k]² across team threads for the Cholesky pivot computation.

Kokkos::single

Kokkos::single(Kokkos::PerTeam(team), lambda)

Executes the lambda on exactly one thread of the team.  Used for operations that must not be duplicated: the Cholesky pivot check and square root in Part V, and the checksum atomic-add in Part VI.

Kokkos::deep_copy

Kokkos::deep_copy(exec, dest, src)

Copies data between Views (device↔device or host↔device).  When given an execution space, the copy is asynchronous on that space's stream.  Used each iteration to reset the RHS vector: deep_copy(exec, x, b) copies the original right-hand side into the working vector before trsm overwrites it.

team.team_barrier()

Synchronizes all threads in a TeamPolicy team.  No thread passes the barrier until all threads reach it.  In Part V's hand-rolled Cholesky, a barrier follows every column's pivot-and-sqrt and every column's trailing update — 2N barriers for N columns.  This is the mechanism that preserves the serial column ordering within a single-team kernel.

Kokkos::atomic_inc / atomic_add

Kokkos::atomic_inc(&counter())
Kokkos::atomic_add(&accumulator(), value)

Thread-safe increment and addition on device-resident scalars (0-D Views).  Used to count Cholesky failures and accumulate the checksum without host round-trips.  The values are read back once after the outer loop completes.

Kokkos single-graph construction (Part VIII)

Kokkos::create_graph

auto graph = Kokkos::create_graph(exec, [&](auto root) {... })

Builds a directed acyclic graph (DAG) of kernel nodes.  The lambda receives a root node; subsequent nodes are added with root.then_parallel_for(...), each returning a node handle that expresses dependencies.  The graph records the kernel sequence but does not execute it.

node.then_parallel_for

auto nB = nA.then_parallel_for(label, policy, lambda)

Adds a parallel_for kernel as a graph node that depends on the parent node.  Returns a handle for chaining further dependencies.  In the non-ArrayView Part VIII path, A, B, status checks, checksum, and E are ordinary graph nodes around the captured solver nodes.

node.cuda_capture

The non-ArrayView Kokkos single-graph source now uses CUDA-backend cuda_capture nodes for the vendor-library section. The captured nodes reset the RHS and call cuSOLVER potrf/potrs on the graph's CUDA stream.

This is intentionally a CUDA 12+ training path. Older compatibility behavior is not the target of this lesson.

graph.instantiate() / graph.submit()

graph.instantiate() locks the DAG topology and prepares it for replay.  graph.submit(exec) enqueues the recorded DAG onto the execution space's stream. In the non-ArrayView Kokkos source path, the outer loop uses one graph.submit(exec) per iteration.

CUDA native functions (Part IX)

cudaLaunchCooperativeKernel

cudaError_t cudaLaunchCooperativeKernel(const void *func, dim3 gridDim, dim3 blockDim, void **args, size_t sharedMem, cudaStream_t stream)

Launches a kernel where all thread blocks must be resident simultaneously on the GPU.  This enables cooperative_groups::this_grid().sync() — a barrier across the entire grid.  The grid size is bounded by the GPU's SM count times per-block occupancy.  Used for the megakernel (one launch per iteration) and persistent kernel (one launch for the entire run).

grid.sync()

cooperative_groups::grid_group grid = cooperative_groups::this_grid();
grid.sync();

A barrier across all thread blocks in a cooperatively-launched kernel.  No block passes until all blocks reach the barrier.  The megakernel uses 4 grid.sync() calls per iteration (after A, B, RHS-reset, and C+D).  The persistent kernel uses 5 (adds one after E for the iteration boundary).  Requires -rdc=true and -lcudadevrt at compile time.

cudaStreamSynchronize

cudaError_t cudaStreamSynchronize(cudaStream_t stream)

Blocks the host thread until all operations on the specified stream have completed.  In the persistent kernel variant, this is the single host-side wait after the cooperative launch — the host has no other work to do while the GPU executes all 50,000 iterations internally.
