# FAT-P

A header-only C++20 library for containers, concurrency, numerical computing,
serialization, and diagnostics. Core utilities have no mandatory third-party
dependencies; optional platform backends and benchmark competitors have separate
requirements.

> ⚠️ **Work in progress** — APIs are not yet stable.

## Overview

FAT-P provides independently includable utilities in the `fat_p` namespace.
Public headers live in [`include/fat_p/`](include/fat_p/); component tests,
benchmarks, and manuals live in [`components/`](components/). Copy the entire
header directory, including its nested implementation directories, or use the
`fatp` CMake interface target.

## How This Library Was Built

Project-owned code, architecture, documentation, and governance were authored by
AI systems — primarily Claude (Anthropic), with contributions from ChatGPT,
Gemini, and Grok. The human ([Matthew Schroeder](Authors.md)) provided direction,
constraints, and judgment. Vendored code in [`ThirdParty/`](ThirdParty/) retains
its upstream authorship and licenses.

The library was developed using independent design, cross-review, synthesis,
focused verification, and context reset cycles. Current contributor and assistant
instructions start at [guidelines/README.md](guidelines/README.md).
[Fat-P AI-Collaborative Development Methodology](documents/Fat-P_AI_Collaborative_Development_Methodology.md)
preserves the historical process; [Authors.md](Authors.md) records attribution.

This is a prerelease project. APIs may change, and passing a particular workflow
does not establish production readiness. See the live workflow links above and
[current verification record](guidelines/CURRENT_VERIFICATION.md) for checked
configurations and known limits. Benchmark reports in
[`benchmark_results/`](benchmark_results/) describe measurements from their
recorded source revisions, machines, and workloads.

## Requirements

* A compiler and standard library supporting C++20.
* CMake 3.21 or newer for the CMake instructions below.
* x64 when using the MSVC CMake build; 32-bit MSVC is explicitly rejected.

The [core CI workflow](.github/workflows/fatp-test-core.yml) defines the current
matrix: GCC 12/13 with C++20 and GCC 14 with C++23, Clang 16 with C++20 and
Clang 17 with C++23, and hosted MSVC with C++20 and `/std:c++latest`. Individual
component workflows may cover additional configurations.

Some facilities select platform-specific backends. For example,
[NumaAllocator](include/fat_p/NumaAllocator.h) uses `libnuma` on Linux when
available, and [Stacktrace](include/fat_p/Stacktrace.h) selects a standard-library,
libunwind, POSIX, Windows, or stub backend. Check the selected component's
requirements and link libraries when using these facilities.

## Installation

```bash
cp -r include/fat_p /your/project/include/
```

Enable C++20 and configure both header search paths. For GCC or Clang's GNU
driver, use `-I /your/project/include -iquote /your/project/include/fat_p`.
For MSVC, use `/I /your/project/include /I /your/project/include/fat_p`.
The short-header path is also needed by nested implementation headers. Copy the
complete directory; the CMake target below configures these paths for you.

Or add FAT-P to an existing CMake project after defining `your_target`. Disable
the repository's test and benchmark targets when consuming only the library:

```cmake
set(FATP_BUILD_TESTS OFF CACHE BOOL "Build FAT-P tests" FORCE)
set(FATP_BUILD_BENCHMARKS OFF CACHE BOOL "Build FAT-P benchmarks" FORCE)
add_subdirectory(path/to/FatP)
target_link_libraries(your_target PRIVATE fatp)
```

Both build options default to `ON` in the repository's top-level CMake file.
If `VCPKG_ROOT` is set, that file automatically selects its vcpkg toolchain.
For the dependency-free core/test builds shown here, unset `VCPKG_ROOT` before
configuring; vcpkg users should supply their own valid toolchain/manifest setup.

Use namespaced includes such as `<fat_p/Tensor.h>`, or quoted short includes
such as `"Tensor.h"`. On Windows with GCC or Clang's GNU driver, CMake keeps the
short-header directory out of the normal `-I` search path so `Signal.h` cannot
shadow the C library's `<signal.h>`. Include the signal component as
`"Signal.h"` or `<fat_p/Signal.h>`.

## Building Tests

```bash
cmake -S . -B build -DFATP_BUILD_TESTS=ON -DFATP_BUILD_BENCHMARKS=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel 2
ctest --test-dir build -C Release --output-on-failure
```

Use a configured compiler environment; on Windows with MSVC, use an x64
developer shell or select an x64 generator. CMake registers component tests as
individual executables; the separate GitHub core workflow builds its aggregate
runner. Check [current verification](guidelines/CURRENT_VERIFICATION.md) for the
latest recorded results and limitations.

## Benchmarks and Documentation

Benchmark sources live in each component's `benchmarks/` directory, alongside
its `tests/` and `docs/` directories where present. Build them separately from
the correctness suite:

```bash
cmake -S . -B build-bench -DFATP_BUILD_TESTS=OFF -DFATP_BUILD_BENCHMARKS=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build-bench --config Release --target benchmark_SlotMap --parallel 2
```

Competitor availability depends on installed libraries, vendored headers, and
the selected platform. For hosted runs, the
[dependency builder](.github/workflows/build-benchmark-deps.yml) prepares shared
caches; [component benchmark workflows](.github/workflows/) restore them. The
[all-component dispatcher](.github/workflows/run-all-benchmarks.yml) builds the
caches before starting those workflows. Reports and raw historical logs are in
[`benchmark_results/`](benchmark_results/); component-specific measurements also
live under `components/<Component>/results/` where present.

Start with component user manuals under [`components/`](components/) for API
contracts, [`Teaching/`](Teaching/) for explanatory material, and
[CONTRIBUTING.md](CONTRIBUTING.md) for the contribution process.
