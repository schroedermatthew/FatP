WHY THIS IS THE RIGHT CALL:
═══════════════════════════

1. Type Safety
   std::any: Runtime crashes waiting to happen
   Alternative: Compile-time guarantees

2. Readability
   std::any: What's in there? Who knows!
   Alternative: Types document themselves

3. Debuggability
   std::any: Good luck stepping through any_cast failures
   Alternative: Clear type errors at compile time

4. Maintainability
   std::any: Future developers curse your name
   Alternative: Future developers thank you

5. Performance
   std::any: Heap allocations, vtable overhead, cache misses
   Alternative: Zero-overhead abstractions

REFACTORING STRATEGIES:
══════════════════════

Option 1: Proper Typed Struct (BEST)
────────────────────────────────────
Instead of:
  std::unordered_map<std::string, std::any> settings;
  settings["max_threads"] = 4;
  settings["host"] = std::string("localhost");
  settings["timeout"] = 30.5;
  // Runtime error if you get the type wrong!

Use:
  struct Settings {
      int max_threads;
      std::string host;
      double timeout;
  };
  CPP_JSON_DEFINE_TYPE_NON_INTRUSIVE(Settings, max_threads, host, timeout)
  
  Settings settings{4, "localhost", 30.5};
  // Compiler catches ALL errors!

Benefits:
  ✓ IDE autocomplete works
  ✓ Compile-time type checking
  ✓ Self-documenting
  ✓ Easy to serialize with our library
  ✓ Zero runtime overhead

Option 2: std::variant (If Types Vary)
──────────────────────────────────────
If value truly can be multiple types:

  using ConfigValue = std::variant<int, double, std::string, bool>;
  std::unordered_map<std::string, ConfigValue> settings;
  
  // Use std::visit for type-safe access:
  std::visit([](auto&& value) {
      using T = std::decay_t<decltype(value)>;
      if constexpr (std::is_same_v<T, int>) {
          // Handle int
      } else if constexpr (std::is_same_v<T, std::string>) {
          // Handle string
      }
      // etc.
  }, settings["key"]);

Benefits:
  ✓ Known set of types (documented in variant)
  ✓ Compile-time exhaustiveness checking
  ✓ std::visit forces you to handle all cases
  ✓ Better performance than std::any

Option 3: Separate Maps (Simplest)
──────────────────────────────────
If keys don't overlap:

  struct Settings {
      std::unordered_map<std::string, int> int_settings;
      std::unordered_map<std::string, std::string> string_settings;
      std::unordered_map<std::string, double> double_settings;
  };

Benefits:
  ✓ Crystal clear what type each setting is
  ✓ Zero ambiguity
  ✓ Trivial to serialize

Option 4: Tagged Union Pattern
───────────────────────────────
For complex heterogeneous data:

  struct Setting {
      std::string key;
      enum class Type { Int, String, Double };
      Type type;
      union {
          int as_int;
          double as_double;
          // For non-trivial types, use std::aligned_storage
      };
      std::string as_string;  // Outside union for std::string
  };

Benefits:
  ✓ Explicit type tracking
  ✓ Minimal overhead
  ✓ Forces conscious type handling
