# Backend Policies Design - Tensor Library

## Overview

The backend policies design properly integrates computation backends (like Intel MKL) as **first-class policy parameters** in the tensor template, following the library's core design philosophy.

## Architecture

### Before (Inheritance-Based)
```cpp
// Old approach - backend as template parameter but using inheritance
template <typename T, typename AllocImpl, typename ConcurrencyPolicy, typename Backend>
class TensorMKL : public Tensor<T, AllocImpl, ConcurrencyPolicy> { ... };
```

### After (Pure Policy-Based)
```cpp
// New approach - backend as pure policy
template <typename T, typename AllocImpl, typename ConcurrencyPolicy, typename BackendPolicy>
class TensorWithBackend : public Tensor<T, AllocImpl, ConcurrencyPolicy> { ... };
```

## Key Components

### 1. TensorBackendPolicies.h

Defines backend policies that provide static methods for operations:

```cpp
struct DefaultBackendPolicy {
    static constexpr const char* name = "Default";
    static constexpr bool has_optimizations = false;
    
    template <typename T>
    using is_supported = std::true_type;
    
    // No specialized implementations
};

struct MKLBackendPolicy {
    static constexpr const char* name = "Intel MKL";
    static constexpr bool has_optimizations = true;
    
    template <typename T>
    using is_supported = /* float/double only */;
    
    // Specialized implementations
    template <typename T>
    static void matmul(const T* A, const T* B, ...);
    
    template <typename T>
    static T dot(const T* x, const T* y, ...);
    
    // ... more operations
};
```

### 2. TensorWithBackend.h

Tensor class that dispatches to backend policies:

```cpp
template <typename T, typename AllocImpl, typename ConcurrencyPolicy, typename BackendPolicy>
class TensorWithBackend : public Tensor<T, AllocImpl, ConcurrencyPolicy> {
    // Dispatch to backend if available and type supported
    Expected<TensorWithBackend, std::string> matmul(const TensorWithBackend& other) const {
        if constexpr (backend_supports_type_v<BackendPolicy, T>) {
            return matmul_backend(other);  // Uses BackendPolicy::matmul
        } else {
            return matmul_default(other);  // Uses base implementation
        }
    }
};
```

## Design Benefits

### 1. Zero-Overhead Abstraction
```cpp
// Default backend: No runtime cost
TensorWithBackend<int, ..., DefaultBackendPolicy> tensor;  
// Compiles to exactly the same code as base Tensor

// MKL backend with unsupported type: Compile-time fallback
TensorWithBackend<int, ..., MKLBackendPolicy> tensor;
// static_assert prevents wrong usage, falls back at compile time
```

### 2. Type Safety
```cpp
// Compile-time type checking
backend_supports_type_v<MKLBackendPolicy, double>  // true
backend_supports_type_v<MKLBackendPolicy, int>     // false

// Safe dispatch
if constexpr (backend_supports_type_v<Backend, T>) {
    // Use optimized path
} else {
    // Use default path
}
```

### 3. Graceful Degradation
```cpp
// MKL not available? No problem!
#if CPP_UTILITIES_HAS_MKL
    // Full MKL implementation
#else
    struct MKLBackendPolicy {
        template <typename T>
        using is_supported = std::false_type;  // Always fall back
    };
#endif
```

### 4. Extensibility
```cpp
// Add new backends easily
struct CUDABackendPolicy {
    static constexpr const char* name = "CUDA";
    
    template <typename T>
    using is_supported = /* GPU types */;
    
    template <typename T>
    static void matmul(...) { /* CUDA kernel */ }
};

// Use it
TensorWithBackend<float, ..., CUDABackendPolicy> gpu_tensor;
```

## Usage Examples

### Example 1: Basic Usage

```cpp
#include "TensorWithBackend.h"

int main() {
    // Automatic backend selection
    TensorDoubleMKL A(TensorShape({1000, 1000}), 1.0);
    TensorDoubleMKL B(TensorShape({1000, 1000}), 2.0);
    
    // Uses MKL GEMM if available
    auto C = A.matmul(B);
    
    return 0;
}
```

### Example 2: Backend Selection

```cpp
// Force default backend
TensorWithBackend<double, StandardAllocatorImpl<double>, 
                  SingleThreadedPolicy, DefaultBackendPolicy> 
    tensor_default;

// Request MKL backend
TensorWithBackend<double, StandardAllocatorImpl<double>,
                  SingleThreadedPolicy, MKLBackendPolicy>
    tensor_mkl;

// Or use convenient alias
TensorDoubleMKL tensor_mkl;  // Same as above
```

### Example 3: Type-Safe Operations

```cpp
TensorDoubleMKL a({5}), b({5});
// ... fill data ...

// MKL-optimized operations (when available)
auto dot_result = a.dot(b);      // Uses cblas_ddot
double norm = a.norm();          // Uses cblas_dnrm2
a.axpy(2.0, b);                  // Uses cblas_daxpy
a.scale(0.5);                    // Uses cblas_dscal
```

### Example 4: Integer Fallback

```cpp
// Integer tensor with MKL backend
TensorWithBackend<int, ..., MKLBackendPolicy> int_tensor;

// Automatically uses default implementation (no MKL for int)
auto result = int_tensor.matmul(int_tensor);  // Works!
```

### Example 5: Runtime Backend Control

```cpp
#include "TensorBackendPolicies.h"

int main() {
    // RAII-based thread control
    {
        MKLContext ctx(8);  // Use 8 threads
        
        TensorDoubleMKL A(...), B(...);
        auto C = A.matmul(B);  // Uses 8 threads
    }
    // Original thread count restored
    
    return 0;
}
```

## Policy Trait System

### Type Support Detection

```cpp
// Check if backend supports type
template <typename Backend, typename T>
inline constexpr bool backend_supports_type_v;

// Usage
static_assert(backend_supports_type_v<MKLBackendPolicy, double>);
```

### Operation Support Detection

```cpp
// Check if backend provides operation
template <typename Backend>
inline constexpr bool has_matmul_v;

// Usage in dispatch
if constexpr (has_matmul_v<Backend> && backend_supports_type_v<Backend, T>) {
    // Use backend implementation
}
```

## Comparison with Other Designs

### vs. Runtime Dispatch (Virtual Functions)
```cpp
// ❌ Runtime dispatch (slow, not extensible)
class Backend {
    virtual void matmul(...) = 0;
};

// ✅ Policy-based (zero-overhead, extensible)
struct BackendPolicy {
    static void matmul(...);
};
```

### vs. Free Functions
```cpp
// ❌ Free functions (no type safety, manual selection)
void mkl_matmul(...);
void cuda_matmul(...);
// User must call correct function

// ✅ Policy-based (type-safe, automatic selection)
tensor.matmul(other);  // Automatically dispatches
```

### vs. Preprocessor Macros
```cpp
// ❌ Preprocessor (not type-safe, hard to maintain)
#ifdef USE_MKL
    mkl_gemm(...);
#else
    default_matmul(...);
#endif

// ✅ Policy-based (type-safe, clean)
if constexpr (Backend::has_optimizations) {
    Backend::matmul(...);
}
```

## Integration with Library Components

### With AllocationStrategy
```cpp
TensorWithBackend<double, PoolAllocatorImpl<double, 1000>,
                  SingleThreadedPolicy, MKLBackendPolicy> tensor;
// Works seamlessly!
```

### With ConcurrencyPolicies
```cpp
TensorWithBackend<double, StandardAllocatorImpl<double>,
                  MutexSynchronizationPolicy, MKLBackendPolicy> tensor;
// Thread-safe MKL operations!
```

### With Expected
```cpp
auto result = tensor.matmul(other);
if (!result.has_value()) {
    std::cerr << "Error: " << result.error() << "\n";
}
```

## Performance

### Compile-Time Overhead
- **Zero**: All dispatch resolved at compile time
- Template instantiation equivalent to base class

### Runtime Overhead
- **Zero** for default backend
- **Zero** for MKL backend (direct function calls)
- **Zero** for type-based fallback (compile-time check)

## Migration Guide

### From Old TensorMKL.h

```cpp
// Old way
#include "TensorMKL.h"
TensorMKL<double, ..., MKLBackend> tensor;

// New way
#include "TensorWithBackend.h"
TensorWithBackend<double, ..., MKLBackendPolicy> tensor;
// Or use alias
TensorDoubleMKL tensor;
```

### Minimal Changes Required

The new design is mostly a drop-in replacement:
1. Include `TensorWithBackend.h` instead of `TensorMKL.h`
2. Use `TensorDoubleMKL` alias (same as before)
3. API remains identical

## Advantages Summary

✅ **Pure policy-based design** - First-class template parameter  
✅ **Zero-overhead** - All dispatch at compile time  
✅ **Type-safe** - Compile-time checking of backend support  
✅ **Extensible** - Easy to add new backends  
✅ **Graceful degradation** - Works without specialized backends  
✅ **STL-compatible** - Works with standard algorithms  
✅ **Thread-safe** - Integrates with concurrency policies  
✅ **Maintainable** - Clear separation of concerns  
✅ **Testable** - Easy to test each backend independently  

## Conclusion

The backend policy design exemplifies the library's philosophy:
- **Zero-overhead abstractions**: No runtime cost for flexibility
- **Type safety**: Compile-time checks prevent errors
- **Extensibility**: Easy to add new backends
- **Composability**: Works with all other policies

This is **the right way** to integrate computational backends in modern C++.
